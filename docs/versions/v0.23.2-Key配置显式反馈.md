# v0.23.2 — Key 配置的显式成功声明（补丁）

> 用户诉求："配置 api-key 之后没有确认按钮，无法知道是否可用，希望显式声明让用户
> 知道配置成功了"。2026-11-18。

## 根因

两处静默叠加：
1. `placeholder="已保存（输入即覆盖）"` 只在输入框**为空**时可见——而配好的 Key
   恒为非空，这个"已保存"提示永远不显示（等于没有）；
2. 「测试连通性」的验证结果是一次性的（只有当次横幅），刷新后无从知道"这把 Key
   是不是已经验证过可用"。

## 功能清单

- **保存回执**：API Key 输入框下方实时状态行——`保存中…`（350ms 防抖落盘期间）→
  `✓ API Key 已保存`（落盘成功）→ 2.5s 后回落让位给验证提示；写盘失败显示
  `保存失败，请重试`。
- **验证记录持久化**：settings 新增 `verified: Record<providerId, { at, tail, len }>`
  ——「测试连通性」成功时写入 { 时间, Key 末 4 位+长度 指纹 }。Key 字段下方：
  - 指纹匹配 → `✓ 此 Key 已验证可用（日期）`（持久显示，重启仍在）；
  - Key 修改后指纹失配 → `⚠ Key 已修改，请重新测试`（改回原 Key 恢复"已验证"）；
  - 从未验证 → `尚未验证可用性——点下方「测试连通性」确认`。
- 防抖队列支持落盘回执：`queue(settings, onSettled?)`——连续输入时中间回调丢弃，
  只有最终落盘对应的回调触发。

## 文件级实现细节

| 文件 | 内容 |
|---|---|
| `settings-debounce.ts` | pending 变 `{settings, onSettled}`；fire 后 `Promise.resolve(persist).then(ok/fail)` 触发回执 |
| `settings.ts` | `queueSettingsSave` 透传 onSettled；AppSettings 加 `verified?`；normalize 逐条结构校验（非对象/缺字段丢弃） |
| `SettingsTab.tsx` | `keyState`（saving/saved/error + saved 2.5s 自动回落 + 切提供商归位）；runTest 成功写 verified 记录（deps 补 persist/t）；Key 字段下状态行（四态 + 指纹失配分支） |
| `settings-debounce.test.ts` | +3 例（ok 回执 / 失败回执 / 中间丢弃）——断言前让出微任务（onSettled 异步触发） |

## 设计取舍

1. **指纹而非明文**：verified 记录只存 Key 末 4 位 + 长度——足够判断"当前输入的是
   不是验证过的那把"，不可还原（备份导出含此字段也安全）。
2. **修改 Key 不清除记录**：改回原 Key 恢复"已验证"（指纹重新匹配）——比"修改即
   清除"更符合直觉，也避免重复消耗测试请求。
3. **保存回执与验证提示分层**：saved 态显示 2.5s 后自动回落，让位给「已验证可用」
   的持久提示——两句话不抢一行。
4. **auto-test 不做**：Key 保存后自动发测试请求会消耗 token 且在断网时产生误导性
   失败；显式的「测试连通性」按钮 + 持久验证记录是更可预期的确认路径（用户诉求的
   "确认按钮"本就存在，缺的是结果可见性——本轮补齐）。
