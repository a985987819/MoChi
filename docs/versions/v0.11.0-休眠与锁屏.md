# v0.11.0 — 休眠与锁屏（P0 收尾）+ 任务板落地

## 目标

v0.10.0 的体检清单里 P0 还剩两条：**没有电源/锁屏事件**、**全程无声**。本版收掉前者，
并把"接下来谁做什么"写进仓库（`docs/tasks/`），让其他 agent 能直接认领。

选这条而不是音效的原因：休眠恢复是**可验证的工程问题**（有确定的行为契约），
音效是**听感问题**——没有真机听感反馈时做进去就是在赌，风险更高。

## 功能清单

- [x] 原生节拍携带 `{ gap_ms, locked }`：1s 的 `sleep` 被系统冻结，醒来第一拍的 `elapsed`
      就是"实际睡了多久"——这是 JS 侧拿不到的信息。
- [x] `services/system-events.ts`：把节拍翻译成 `state://system-resumed`（≥5s = 恢复，
      ≥5min = `burst`）与 `state://session-lock-changed`。
- [x] **锁屏视为离开**：`GetForegroundWindow()` 无有效句柄 → 立刻按 away 处理，
      不等到 5 分钟空闲阈值（否则锁屏后头 5 分钟仍可能把提醒弹到锁屏界面）。
- [x] **休眠恢复合并交付**：长休眠恢复时，积压的过期提醒合并成一条「N 条提醒到点了」，
      正文按时间顺序列出（最多 5 条 + 「等 N 条」），不再连弹多个。
- [x] 恢复后活动段从零重算（`activeMinutes` 不再把整晚睡眠算成陪伴时长）。
- [x] **任务板**：`docs/tasks/README.md`（认领协议 + DoD）、`TASKS.md`（总表 + 已完成考古 +
      明确不做）、7 个未完成任务文件；`AGENTS.md` 增加「开工前先看任务板」。
- [x] 版本对齐 0.11.0，安装包 `run_here/windows/Mochi_0.11.0_x64-setup.exe`。

## 文件级实现细节

### Rust（`src-tauri/src/lib.rs`）

- `start_native_tick` 维护 `last_tick: Instant`，每拍算 `gap_ms` 并随事件发出；
  事件载荷从 `()` 变成 `{ gap_ms, locked }`——两个既有订阅方都不读载荷，向后兼容。
- 新增 `session_locked()`：Windows 用 `GetForegroundWindow().is_invalid()`，
  其它平台恒 `false`。**只问"有没有前台窗口"**，不读标题/进程（隐私红线的延续）。

### 系统事件（`src/services/system-events.ts`，新增）

- 纯函数 `classifyTickGap(gapMs)` → `null | "resume" | "burst"`，阈值 `RESUME_GAP_MS=5s`、
  `BURST_GAP_MS=5min`；
- 纯函数 `formatBatchBody(texts, limit=5)`：最多列 5 条 + 「等 N 条」，空文本剔除；
- `startSystemEvents()` 返回释放函数，由 `hostServices` 托管（注册失败 5 秒重试、HMR 释放）。

### 在场（`src/services/presence.ts`）

- 抽出 `applyPresence(next)` 作为**唯一状态出口**（宠物状态 / 订阅者 / 跨窗口广播三处同步）；
- `handleSessionLock(locked)`：锁屏 → 立刻 away；解锁 → 立即重算；
- `handleResume()`：`lastObservedAt` 清空、`activeSince = now`、立即重算；
- `cleanup` 从单个函数改成数组（多了两个监听）。

### 提醒（`src/services/reminders.ts`）

- 订阅 `systemResumed`：`burst=true` 时置 `burstResume` 标记并立即扫描；
- `coalesceOverdue(now, generation)`：把 `active AND fire_at<=now` 的 ≥2 条提醒认领并合并成**一条**弹窗，
  同时写 `acknowledged_at`——不写的话下一拍会被"未确认提醒恢复"逐条重新弹出，绕回轰炸；
- 合并提醒也写一条聊天历史，用户能在聊天窗看到"那晚错过什么"。

### 任务板（`docs/tasks/`，新增）

`README.md`（认领协议 / 状态机 / DoD / 与 roadmap 的分工）、`TASKS.md`（7 个 open 任务 + 6 个已完成 +
3 个"明确不做"）、7 个任务文件；`AGENTS.md` 增加第 4 条铁律指向它。

## 设计取舍

**① 为什么用"节拍间隔"而不是系统电源事件 API**
真正监听 `WM_POWERBROADCAST` 需要在窗口过程里挂子类化，Windows 专属、macOS 另写一套，
而且注册失败时没有任何降级。节拍间隔是**跨平台且必然可用**的信号：线程被冻结多长，
`Instant::elapsed` 就多长。代价是"只知道睡了多久，不知道是休眠还是疯狂卡顿"——
但对合并提醒这件事，两者该采取的动作是一样的。

**② 为什么锁屏用"有没有前台窗口"当判据**
`WTSQuerySessionInformation` 之类的正经 API 需要额外的 crate 与权限；而锁屏/安全桌面下
前台窗口句柄必然无效。这是启发式，但**只读几何/句柄，不读内容**，与 `docs/learning/08` §3 一致。
误判方向也安全：判成离开只是少弹一次提醒。

**③ 为什么合并提醒要写 `acknowledged_at`**
提醒表用"`fired` 且未 `acknowledged`"表示"用户还没看到，重启要恢复"。合并提醒把多行一次交付，
如果不标已确认，下一拍就会被恢复逻辑逐条弹出来——正好抵消了合并的意义。
代价：这些行从此不会被单独重发（信息在合并正文与聊天历史里）。

**④ 为什么单条不合并**
只有一条时走常规通道更好：原文完整、有「确认/稍后」交互。合并只在"≥2 条且刚经历长休眠"时发生。

**⑤ 任务板为什么放仓库而不是 issue**
这个项目是"单人 + 多 agent"协作，agent 进不来 GitHub issue；写进 `docs/tasks/` 才能被
任何一个会话读到，而且能跟 AGENTS.md / roadmap / versions 形成完整闭环。

## 踩坑与解决

### ① 信号源只有一个，必须说清边界

`systemResumed` 无法区分"休眠"与"服务卡了 30 秒"。文档里明确写：它只用于"重算在场"与
"合并积压提醒"，不要拿它做"用户刚回来"的语义判断（那个用 `presence`）。

### ② 对照实验的教训（沿用 v0.10.0）

验证合并提醒时不能"启动后直接等"——启动瞬间调度器可能已经把过期提醒逐条投递了。
正确姿势：先让应用跑起来，再插入过期数据，再触发 `system-resumed{burst}`，才能干净地验证合并路径。
本次就是这样测的（见自测清单）。
