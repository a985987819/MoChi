# v0.17.0 — 数据备份 / 导入 / 迁移（P2-02）

> 任务单：`docs/tasks/P2-02-数据备份.md`。完成于 2026-11-18。

## 目标

换机/重装/误删有恢复路径：一键导出 zip（三数据源 + manifest）、从备份列表导入、
覆盖前自动 pre-restore。

## 功能清单

- **导出**：`{appData}/backups/mochi-YYYYMMDD-HHmmSS.zip`，内容 = `manifest.json`
  （appVersion/exportedAt/includeKeys/schemaVersion）+ `settings.json` + `mochi.db`
  + `pet-assets/`；默认**不含 API Key**，勾选才包含。
- **导入**：设置页列出备份目录的 zip（时间倒序 + 体积）→ 两步确认（导入 → 确认覆盖）
  → 覆盖前自动 `pre-restore-*.zip`（恒含密钥）→ 覆盖三数据源 → 提示重启生效。
- **安全**：zip 条目白名单（zip slip 防护）、总量 512MB / 单条目 256MB 上限、
  manifest schemaVersion 拒绝"更新版本倒灌"、导入路径必须落在 backups 目录内。
- **导出前 WAL checkpoint**（前端执行 `PRAGMA wal_checkpoint(TRUNCATE)`，尽力而为）。

## 设计取舍

1. **不用 tauri-plugin-dialog**（任务单要求先确认）：为一次低频操作加插件 +
   capability 不值得。退化方案收敛且自洽——导出固定目录 + reveal 一键可达；
   导入从列表选（外部备份文件拖进 backups 目录即可被识别）；导入路径 Rust 侧
   canonicalize 后必须落在备份目录内，防 IPC 任意路径写。
2. **数据库替换走"改名腾位 → 临时名落位 → 改名归位"**：应用运行时 SQLite 可能
   持有打开的文件句柄，直接覆盖在 Windows 上会被拒绝。改名若失败（无
   share-delete），在动任何数据**之前**就报错退出（提示先从托盘完全退出再导入）；
   写入失败则把旧库还原回去。旧 `-wal`/`-shm` 一律删除（它们属于被替换的旧库）。
3. **导入先全量校验、再 pre-restore、最后才动数据**：半途报错等于现场被毁——
   白名单/schema/必要文件检查全部通过才生成 pre-restore，生成失败即中止。
4. **pre-restore 恒含密钥**：它是覆盖前的退路，退路不能比现场贫瘠（密钥丢了
   就真的丢了）。普通导出默认不含密钥（备份文件容易被拷走）。
5. **appConfigDir vs appDataDir 的坑**：plugin-sql 把 sqlite 文件放 appConfigDir，
   store/pet-assets 放 appDataDir——在 Windows（Roaming）与 macOS（Application
   Support）两者指向**同一个物理目录**，备份统一按 appDataDir 处理是正确的；
   Linux 上二者不同（本项目不面向 Linux，版本文档记录这个边界）。
6. **checkpoint 放前端**：写连接（plugin-sql 连接池）在前端，PRAGMA 必须从持有
   连接的一侧执行；Rust 侧只拷文件。与其他窗口读并发冲突时 checkpoint 返回
   busy——导出数据最多落后几秒，可接受降级（日志有痕）。

## 踩坑与解决

- `import_backup_impl` 初版写成 async + await 自己的同步返回——编译器直接指出，
  去掉 await（同步实现跑在 async 命令的 tokio 线程上，语义等价）。
- `asBackupInfo` 的 `Number.isFinite` 不收窄类型——显式 `typeof` 检查。

## 备份文件里有没有明文 Key？（任务单验收要求）

| 备份类型 | settings.json 内容 |
|---|---|
| 普通导出（默认） | `apiKeys: {}`——**没有**明文 Key（strip_api_keys 纯函数清空，Rust 单测覆盖） |
| 普通导出（勾选「包含密钥」） | **有**明文 Key——用户显式勾选，UI 文案已警示 |
| pre-restore 自动备份 | **有**明文 Key（退路必须完整，留在本机 backups 目录） |
