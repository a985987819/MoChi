## 文件级实现细节

### 数据集（规模说明）

规划 ~130 条，实际 **100 条**——取舍原则"宁缺勿编"：只收录有把握给出合理约值的常见条目，凑数的高错误率条目比缺条目更伤信任。扩展路径：新条目加进对应品牌 JSON 即生效（索引启动重建）。每条 serving 明确（"1个/1份（中）/1块（整份的1/8）"），比萨按块计量避免整张歧义。

### 管线

- 查询：`expandQuery`（组内 every 跳过=幂等 + 全小写比对）→ `BM25Retriever.search`
- 输出：`{count, results[{id,brand,name,serving,kcal,protein,fat,carbs,score}]}` —— score 供模型做相对置信表达
- 空结果语义：count=0 → 模型按系统提示说"没查到"+ 近似项标注

### 提示词生长（prompt.ts diff）

能力边界段新增：热量数值只能来自 search_food 条目、逐条注明品名与份量、近似品标注、合计相加（≤5 项，07 §5）、2000 kcal 参考基准。

## 设计取舍

1. **数据集 100 条而非凑满 130**：数值可信度 > 条目数（07 判据 2 错误代价）；扩展零成本。
2. **agentic RAG（检索作为工具）而非每轮强制注入**：闲聊不浪费检索；模型自主判断何时查（05 §6 既定裁决落地）。
3. **expandQuery 幂等 + 全小写输出**：评测抓到两个真问题（不幂等、大小写不稳定），修复以符合规格——细节见踩坑。
4. **工具输出剥 aliases**：模型不需要别名列表（它自己产出别名），省窗口（03 工具结果瘦身）。
5. **比萨按 1/8 块计量**：整张/块的单位歧义是热量问答的高频错源，serving 明确到不可再分。

## 踩坑与解决（评测驱动的两连修复）

| 问题 | 原因 | 解决 |
|---|---|---|
| expandQuery 不幂等 | 二次扩展时触发词仍在（组只查 some 未查 every），组被重复追加 | `every` 跳过已扩展组 |
| 幂等后输出仍不稳定 | 幂等检查用原大小写词比对已小写化的 q（"KFC" 永远 miss）+ 附加文本保留原大小写 | 比对与附加统一走小写 |
| 测试期望错误 ×3（v0.5.0 批次遗留经验的延续） | 同义词测试与分词顺序断言未按实现语义写 | 以实现语义修正断言并补注释 |
