# 07 · 边界划分：哪些归 Agent，哪些归桌面应用

> 适用：全部版本 ｜ 性质：架构裁决文档——新功能入清单前，先过本文的判定框架
> 学完标准：拿到任何新功能需求，能按 §2 的流程给出归属结论，并能说出三条理由。

## 1. 一句话判据与结论速览

> **Agent 负责"理解意图与组织语言"；应用负责"精确执行、守时守数、持有状态"。**
> 即使决策归了 Agent，**执行层永远在应用侧**（Agent 工具只是应用服务的薄封装）。

Mochi 全部功能的归属速览（详细论证见 §4）：

| 功能 | 意图/决策层 | 执行层 | 模式 |
|---|---|---|---|
| 对话/闲聊/陪伴 | Agent | Agent（生成） | 纯 Agent |
| 宠物情绪状态（happy/sad…） | **Agent** | 应用（PetStateManager 仲裁渲染） | 决策代理 |
| 待办的自然语言增/查 | **Agent** | 应用（TodoService + SQLite） | 双入口 |
| 待办的 UI 增/删/勾选 | 用户点击 | 应用 | 双入口 |
| 番茄钟启停 | 用户点击 或 **Agent** | 应用（TimerService 状态机） | 双入口 |
| 番茄钟计时/阶段切换 | —— | **应用** | 纯应用 |
| 站立提醒（计时/弹窗/重置） | —— | **应用** | 纯应用 |
| 热量数值检索（BM25） | —— | **应用** | 纯应用 |
| 热量问答/解读/搭配建议 | **Agent** | Agent（基于检索结果生成） | 检索增强 |
| 营养数值合计 | —— | 应用/工具（防模型算错） | 纯应用 |
| 长期记忆写入 | **Agent**（remember，受约束） | 应用（MemoryService） | 决策代理 |
| 记忆检索注入 | —— | 应用（每轮 context-builder） | 纯应用 |
| 会话历史持久化 | —— | **应用** | 纯应用 |
| 设置（Key/提供商/间隔参数） | 用户表单 | 应用 | 纯应用 |
| ~~通过对话改设置~~ | （v1 否决） | —— | 灰色地带，见 §5 |
| 窗口/托盘/通知/生命周期 | —— | **应用（Rust）** | 纯应用 |
| 宠物素材加载/回退 | —— | **应用** | 纯应用 |
| 数据集（营养 JSON）维护 | 人工编辑 | 应用资产 | 纯应用 |

一眼可见的结构：**纯 Agent 的只有"生成类"任务；纯应用的是一切有确定性要求的；最多的一类是"双入口/决策代理"——Agent 理解、应用执行。**

## 2. 判定框架：四问决策树 + 八条判据

### 2.1 决策树（新功能先走一遍）

```
Q1 这个行为需要理解"模糊的人类意图"吗？
   （自然语言、口语别名、"那个辣的"这类指代）
   ├─ 是 → 意图层归 Agent。继续 Q2 决定执行层归谁。
   └─ 否 → 转 Q3

Q2 执行时需要"精确保证"吗？（时间精确到秒 / 数值精确无幻觉 /
   事务原子性 / 必须在无网无 Key 时也发生）
   ├─ 是 → 执行层归应用；Agent 只通过工具下发指令（工具内校验）
   └─ 否 → 且属于生成性内容（文案/解释/建议）→ 执行也可归 Agent

Q3 它需要 <100ms 响应或极高频触发吗？（点击、拖拽、勾选）
   ├─ 是 → 应用代码（过 LLM 的时延 1~5s、按 token 计费，撑不住）
   └─ 否 → Q4 离线/无 Key 时必须可用吗？
       ├─ 是 → 应用代码
       └─ 否 → 才考虑 agent 化（且仍应保留 UI 直操作入口）
```

### 2.2 八条判据（决策树背后的量化依据）

| # | 判据 | 倾向应用 | 倾向 Agent |
|---|---|---|---|
| 1 | 确定性 | 同输入必须同输出（计时、求和） | 允许可变的表达（措辞、语气） |
| 2 | 错误代价 | 错一次就出事（漏提醒、算错账） | 错了能被用户包容（措辞不完美） |
| 3 | 时延要求 | <100ms（UI 反馈） | 1~5s 可接受（问答） |
| 4 | 触发频率 | 每分钟多次 | 每轮对话几次 |
| 5 | 可用性 | 离线/无 Key 必须工作 | 可依赖网络与 Key |
| 6 | 单次成本 | 必须为零 | 可承受 token 费用 |
| 7 | 可测试性 | 能写确定性单测（断言相等） | 需评测集抽样验收（Hit@3、人工评审） |
| 8 | 安全等级 | 高危/不可逆（删库、改 Key） | 低危可回滚（发条消息） |

用法：给功能的每个"动作"打分，**多数判据倾向哪边就归哪边；判据冲突时，以 1、2、8（确定性/代价/安全）为一票否决项**——宁可笨一点，不可错一点。

### 2.3 三层归属模型（比"二分"更精确）

把每个功能拆成三层分别裁决：

```
意图层（谁理解用户想要什么） → 执行层（谁真的去做） → 存储层（谁是状态的唯一权威）
```

铁律三条：
1. **意图层可以给 Agent**（它就是干这个的）；
2. **执行层几乎总是应用**——Agent 工具 = 应用服务的一层薄壳（校验参数 → 调 Service → 返回结构化结果），绝不在"工具函数里"写业务逻辑；
3. **存储层 100% 归应用**。Agent 没有自己的状态：它的"状态"只有 messages 数组和检索到的上下文。凡是需要跨轮存活的东西都落 SQLite/Store。

这条铁律的业界对应：iOS 的 App Intents + Apple Intelligence（Siri 理解意图 → 调用应用注册的能力）、MCP（应用暴露能力，Agent 编排）。**应用暴露能力、Agent 编排能力**，是全行业收敛的形态。

## 3. 双入口模式（Mochi 最重要的架构推论）

"UI 点击"和"Agent 工具"是同一个功能的两个入口，必须汇入**同一个服务层**：

```
番茄钟按钮 onClick ────────┐
                          ├──→ PomodoroService.start(25) ──→ 状态机/计时/通知
"来个番茄钟" → Agent ──→ start_pomodoro 工具 ──┘
                              （工具内做参数校验 + 边界检查，如"已在专注中"返回 ok:false）
```

收益：
- **一致性**：无论哪个入口，状态只有一个权威来源，UI 自动通过事件刷新；
- **可测试**：Service 层确定性单测；Agent 工具只测"参数→Service 调用"的映射；
- **可裁剪**：Agent 通道坏了（无 Key/网络断），UI 通道完好，核心功能不瘫。

推论：**凡是 Agent 能做的事，必须存在一个不经过 Agent 的等价 UI 操作**（v1 例外：mood 情绪状态——它本来就是对话的产物，无 UI 入口是合理的，因为系统事件兜底了关键状态）。

## 4. 逐功能裁决与理由

### 4.1 纯应用（确定性或系统能力，禁入 Agent）

| 功能 | 裁决理由（对照判据编号） |
|---|---|
| 站立提醒计时/触发/重置 | ①②：必须精确满 60min 且不可漏发；⑤：无 Key 也要提醒；⑧：提醒是核心承诺。**LLM 没有时钟、没有执行的连续性**——"一小时后提醒我"若交给模型去等，会话一关就蒸发了。正确分工：应用计时；Agent 若参与，只在"理解用户想改间隔"这类意图上 |
| 番茄钟计时与状态机 | 同上。25:00 倒数必须走时间戳（`Date.now()` 基准）而非 interval 累加（挂起会漂移）；focus/break 切换是确定的状态机 |
| 窗口/托盘/通知/生命周期 | 系统能力，与智能无关（06 文档：窗口管理收归 Rust） |
| 热量检索（BM25） | ①⑦：检索是确定性算法，可单测可评测（05 文档）；让模型"直接报热量"等于放弃 RAG 的反幻觉防线 |
| 营养数值合计 | ①②：模型做多位加法会出错（token 级算术），组合餐的总量应由工具计算返回（v1 数据量小允许模型口算 ≤5 个数，已在系统提示要求引用条目，v2 补 `verify_meal` 工具硬校验） |
| 记忆检索注入 / 历史持久化 | ①④：每轮都要做，高频+确定性；Agent 不该有"要不要查记忆"的自由（04 文档：写入有决策，读取无脑注入） |
| 设置表单 | ④⑧：改 Key/改间隔是低频高危操作，需要表单的显式性与即时校验 |

### 4.2 纯 Agent（生成性任务）

| 功能 | 裁决理由 |
|---|---|
| 对话/闲聊/情感陪伴 | 本质是生成，无"正确答案"，判据 2 宽容 |
| 热量问答与搭配建议 | 检索（应用）给"依据"，解读、组织回答、给 800 kcal 搭配方案是生成——且系统提示强制"数值只能来自检索条目"，生成被关在引用的笼子里 |
| 宠物情绪决策 | 情绪没有对错，只有"贴不贴合语境"——典型的模糊判断。但注意：**Agent 只是提议者**，应用（PetStateManager）按优先级仲裁：`系统事件(alert/focus) > Agent 情绪 > idle`，且限时自动回落。决策被关进了应用定的规则里 |

### 4.3 双入口 / 决策代理（本项目的主力形态）

| 功能 | 意图层 | 执行层 | 工具风险分级 |
|---|---|---|---|
| 待办：自然语言增/查 | Agent：把"明早九点交周报"解释为 `add_todo({title, due:"明早九点"})` | 应用：TodoService 写 SQLite | write（低危可逆） |
| 待办：UI 直接操作 | 用户点击 | 应用（同一 Service） | —— |
| 番茄钟：对话启停 | Agent：识别"来个番茄钟" | 应用：PomodoroService（校验"已在进行中"） | write（状态性） |
| 记忆写入 | Agent：判断"值得记吗"（受系统提示约束：只记长期偏好、禁敏感信息） | 应用：MemoryService | write（隐私敏感 → 工具描述+系统提示双重门禁） |

风险分级规范（工具设计时标注）：`read`（无副作用）< `write`（可逆变更）< `destructive`（删除/覆盖，v1 的 `delete_todo` 属于轻度破坏性——工具结果要求返回被删条目内容，给用户可追溯性）。v1 无"需确认"级工具；未来出现（如"清空全部记忆"）必须实现**确认回环**：工具返回"待确认"状态 → UI 弹确认 → 用户确认后才真正执行。

## 5. 灰色地带裁决记录（最有学习价值的部分）

| 议题 | v1 裁决 | 理由 | 演进方向 |
|---|---|---|---|
| 对话改设置（"把站立提醒改成 45 分钟"） | **否决**：设置仅 UI | ④低频不值得；⑧误改成本高；对话通道缺"确认 UI"（工具没有来回确认机制） | 引入确认回环后开放为 `update_settings` 工具 |
| 对话设提醒（"1 小时后提醒我喝水"） | **部分**：站立提醒固定逻辑不可改；一次性计时提醒留 backlog | 一次性提醒需新 TimerService 能力，非 agent 问题 | 先做应用能力，再开 agent 工具 |
| 提醒/番茄钟文案 | v1 固定文案 | ①④：弹窗每次都触发，走 LLM 又慢又贵 | 缓存式生成：agent 预生成文案池，弹窗随机取 |
| 模型口算组合餐总热量 | 允许（≤5 项）+ 系统提示要求列式引用 | 数据小、可由用户肉眼复核 | `verify_meal` 工具：应用重算并回填修正值 |
| Agent 自主扩充营养数据集 | **否决** | ⑧：写入权威数据源不可逆 | 开发期用 AI 辅助人工整理，运行时数据集只读 |

**裁决模式总结**：灰色地带先按保守方案落地（应用为主），给演进留接口（工具确认回环、文案池、校验工具）——**边界是可以移动的，但只能带着评测与保障移动**。

## 6. 反模式清单（每条都是真实事故模式）

### 6.1 不该交给 Agent 的（做了必翻车）

1. **让 Agent "等待"或计时**——模型没有执行连续性，会话关闭即消失；时间基准永远在应用。
2. **让 Agent 直接读写数据库/文件**（绕过 Service 校验）——一次幻觉输出 `DELETE` 就没了；工具必须过服务层。
3. **高频 UI 交互走 LLM**——勾选一个待办等 3 秒还花钱，用户会卸载你。
4. **让 Agent 维护自己的状态副本**——与 SQLite 双写必然漂移；状态只有一处权威。
5. **让模型做长算术/日期推算**（"下周三是几号"）——应用给时钟与计算器，模型只做表达。
6. **Agent 输出直接当 HTML/SQL/命令执行**——注入风险；输出先过白名单/参数化。

### 6.2 不该写死在应用里的（做了变呆板）

1. **用正则/关键词表做意图识别**（`if _msg.contains("待办")`）——"帮我记一下明天要…"就漏了；这正是 LLM 的主场。
2. **把所有文案写死成枚举**——桌宠的灵魂在"像活的"；生成类内容该让 Agent 来（配缓存与预算）。
3. **用多级菜单模拟对话**——"你想查询：1. 热量 2. 待办…"式的 UI 是把意图层的活硬塞给执行层。

### 6.3 一票否决自查表（新工具上线前逐项打钩）

- [ ] 这个工具的执行走的是应用 Service 层（而非工具函数内自行实现业务）？
- [ ] 参数经过 Schema 校验 + 边界检查（重复启动、不存在的 id）？
- [ ] 失败返回 `{ok:false,error}` 回传模型自愈，而不是抛异常崩循环？
- [ ] 风险分级（read/write/destructive）已标注，destructive 有可追溯输出？
- [ ] 存在一个不经过 Agent 的等价 UI 操作（或说明为何可以没有）？
- [ ] 无 Key/离线时，对应的核心功能仍有 UI 通道可用？

## 7. 判据速查卡（贴在脑内的 TL;DR）

- **模糊意图、生成表达、语境判断** → Agent
- **精确时间、精确数值、事务、离线必达、<100ms、高频点击** → 应用
- **跨轮存活的任何状态** → 应用存储层，永远
- **Agent 提议，应用裁决**（情绪优先级、参数校验、确认回环）
- **双入口、单服务、一权威**
