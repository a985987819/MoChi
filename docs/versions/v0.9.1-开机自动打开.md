# v0.9.1 — 设置项「开机自动打开」与首启事件时序修复

## 目标

用户在 v0.9.0 收口后提出三件事，本版一次性收口：

1. 检测项目当前能否正常运行；
2. 检测**未配置 API Key** 时能否完成常规任务；
3. 在设置里新增【开机自动打开】功能，并打一个能在 Windows 上直接运行的安装包。

第 3 项实际是**升级既有能力**：v0.9.0 已有「开机自启」（P1-14，接入
`tauri-plugin-autostart`），但（a）命名与文案没有说清「开机后到底发生什么」，
（b）开关只有前端布尔值，没有系统真值回话——安全软件回滚注册表写入时就是
「开关开着、开机不启动」的假成功，（c）实测发现打包版**首启**根本没生效。

## 功能清单

- [x] 设置项更名为「开机自动打开」，文案说明「开机后麻薯出现在桌面右下角、不弹聊天窗」。
- [x] Rust 新增 `get_autostart_enabled` 命令 + `state://autostart-state` 回执：
      执行后用 `is_enabled()` 读回**系统真值**，前端按「意图 vs 真值」展示生效/被拦截/系统残留三态。
- [x] 设置页新增「重新应用」按钮：一键把设置值再写一次系统（自愈被回滚的写入、清理残留启动项）。
- [x] 修复打包版首启 `state://` 事件丢失（原生节拍兜底重放），同时修好 v0.9.0 的
      快捷键/宠物大小在首启不生效的同类隐患。
- [x] 版本对齐 0.9.1：`package.json` / `src-tauri/tauri.conf.json` / `src-tauri/Cargo.toml` + `Cargo.lock`。
- [x] Windows 安装包：NSIS `Mochi_0.9.1_x64-setup.exe`（2.60 MiB）与 MSI（3.61 MiB），已收集到 `run_here/windows/`。

## 文件级实现细节

### Rust（`src-tauri/src/lib.rs`）

- 新增常量 `EVT_AUTOSTART_STATE = "state://autostart-state"`。
- 自启监听器（`setup_ui_event_listeners` 内）在 `enable()/disable()` 之后追加一步
  `autolaunch().is_enabled()` 读回，载荷 `{ enabled: 真值, ok, error? }` 广播；
  `ok` 的判定是「调用成功 **且** 真值与意图一致」——只有这样才能识别
  「调用返回 Ok 但注册表被安全软件回滚」。失败原因同时 `eprintln!`，便于真机排障。
- 新增命令 `get_autostart_enabled(app) -> bool`：设置页挂载时调用，把「设置里的开关」
  与「系统里真实登记的启动项」对齐；读到异常按 `false` 处理（不抛错，不影响其他设置项）。
- 命令注册进 `invoke_handler`。**不新增 capability**：自定义命令不经权限表，
  权限面与 v0.9.0 完全一致。

### 服务层（`src/services/autostart.ts`，新增）

- `applyAutostart(enabled)`：设置页 → `state://autostart-changed`（薄封装，不持业务状态）。
- `readSystemAutostart()`：`invoke("get_autostart_enabled")`，`null` 表示读不到。
- `describeAutostart(desired, system)`：**纯函数**，把「意图 + 真值」翻成三态提示
  （none/ok/warn）。四种错位场景各有独立断言，见单测。

### 设置页（`src/pages/chat/SettingsTab.tsx`）

`AutostartSection` 重写：挂载读一次真值 + 订阅回执；提示条按 `tone` 上色（`chat.css`
新增 `.settings-note--ok/--warn`）；`warn` 时附「重新应用」。开关值仍是设置的事实源。

### 宠物窗启动同步（`src/pages/pet/main.tsx`）

拆出 `syncStartupSettings()`（快捷键/自启/游戏模式/宠物大小四项重放，幂等）与
`maybeOpenOnboarding()`（引导只叫一次），并新增**首启兜底**：监听 `state://native-tick`，
第一拍到达时再重放一次。原因见下节「踩坑与解决」。

### 事件协议（`src/shared/events.ts`）

新增 `STATE_EVENTS.autostartState`，与 Rust 侧常量一一对应。

## 设计取舍

**① 为什么回执而不是让前端直接调插件**
`tauri-plugin-autostart` 只有 Rust API。前端直连要为 pet/chat/alert 三窗口都开自启权限，
扩大权限面；项目纪律是「系统级操作单一所有者」（AGENTS.md / lib.rs 头注释）。所以维持
「前端发事件 → Rust 执行并回执」，只是这次把**结果**补回来。

**② 为什么非要读系统真值**
设置文件是应用私有数据，系统启动项是另一份事实，会因三类现实原因错位：安全软件启动项
防护回滚写入、用户在任务管理器手工禁用、重装到别的目录后旧启动项指向不存在的 exe。
只显示设置值 = 假成功。命令 + 回执两层里，回执负责「刚点完这一下」，命令负责「打开设置页
时对齐」，缺任一层都会有一段时间说假话。

**③ 为什么启动同步用节拍兜底而不是改成命令**
`invoke` 有请求/响应，天然不会丢；但把四项设置各写一个命令，等于把「事件驱动」拆成两套
协议。原生节拍由 Rust 在 setup 之后每秒发一次，正好是「两边都就绪」的确定信号，
复用它的成本最低，且顺带修好了快捷键/宠物大小的同类隐患。

**④ 默认仍然关闭**
不默认自启是桌宠软件的底线：装完就开机自启属于「用户没同意的事」。

## 踩坑与解决

### ① 构建环境：沙箱拦 `reg.exe`

`scripts/vsenv.cmd` 依赖 `vswhere + vcvars64.bat`，后者内部会调用 `reg.exe`，
本机安全策略把 `reg.exe` 列入黑名单，`cargo check` / `pnpm tauri build` 直接失败
（表现为无输出、exit 1）。**处置**：手动构造 MSVC 环境后直接跑 cargo/pnpm，不经过 vcvars：

- `MSVC = C:/Program Files (x86)/Microsoft Visual Studio/2022/BuildTools/VC/Tools/MSVC/14.44.35207`
- `SDK  = C:/Program Files (x86)/Windows Kits/10`，版本 `10.0.26100.0`
- `PATH` 前置 `$MSVC/bin/Hostx64/x64` 与 `$SDK/bin/10.0.26100.0/x64`（同时避免 Git 的 `link.exe` 遮蔽）
- `INCLUDE` / `LIB` 按 MSVC + SDK 的 ucrt/um/shared/winrt/cppwinrt 组合
- 注意 `PATH` 要**前置**而不是覆盖：`pnpm` 在 `F:/NodeJS/node_global`，覆盖会 `command not found`。

### ② 首启自启不生效（本版核心修复）

**现象**：打包版干净首启后 `HKCU\...\Run` 里始终没有 `Mochi`；用 WebView2 远程调试口
手动重载宠物页，1 秒内立刻写入；`pnpm tauri dev`（页面由 vite 提供）也一直正常。

**排查**：`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=92xx` +
CDP 在宠物页里 `invoke('get_autostart_enabled')`（确认命令本身可用）、手动
`plugin:event|emit`（确认事件→Rust→注册表链路可用）；再在 Rust 监听器里临时加
`eprintln!` 并用带控制台的调试版（`pnpm tauri build --debug --no-bundle`）抓启动输出——
日志里只有「监听注册完成」，**没有收到事件**。同时用 `--pet-scale` CSS 变量确认启动
同步代码确实跑过（缩放 1.2 生效）——即「发是发了，Rust 没收到」。

**原因**：webview → Rust 的单向事件在启动瞬间有竞态。前端 `emit()` 的事件若早于
`setup_ui_event_listeners` 注册监听，会被直接丢弃且不报错，`invoke` 本身仍返回成功，
所以 `.catch()` 也捕获不到。内嵌资源加载远快于 vite，于是只有「打包版 + 首启」命中；
v0.9.0 的快捷键、宠物大小有同样的暴露面。

**修复**：宠物窗在首拍 `state://native-tick`（Rust setup 之后才开始、每秒一次）上重放一次
启动同步；四项重放均幂等（快捷键先注销再注册、自启 enable/disable 幂等、尺寸重设、游戏模式只置标志位）。
**验证**：干净首启 t+1s 写入启动项（指向 release exe），把设置改为关闭再启动 t+1s 移除。

### ③ 打包时 exe 被占用

上一轮验证进程没退出 → `failed to remove file ... mochi.exe`（os error 5，拒绝访问）。
顺序固定为「先结束进程并确认 `remaining=0`，再打包」。
