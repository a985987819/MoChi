## 0. 执行契约（先读完这一节再动手）

### 0.1 你在这个项目里的角色

你接手的是一个**已经能跑、已经在分发**的 v0.8.x 应用。它的问题不是"缺功能"，而是
"第一次用的人不知道从哪下手、天天用的人觉得差点意思"。所以今晚的工作重心是
**体验与可靠性**，不是加新赛道（不要做语音、不要做多模态、不要做云同步）。

判断一个任务该不该做的三问：

1. 用户会不会在**头 5 分钟**遇到它？（会 → 高优先级）
2. 它是不是**已经承诺过但没做到**的功能？（是 → 高优先级，属于修 bug）
3. 它会不会让代码更难懂？（会 → 除非有教学价值，否则不做）

### 0.2 一个任务 = 一个循环

```
读任务 → 读相关文件与 learning 文档 → 改代码 → 补/改测试 → 跑门禁
      → 更新 docs/versions 记录 → 结构化提交 → 下一个任务
```

**禁止攒批提交。** 一个任务一个 commit，commit message 按 §8 的模板写。
一晚上 20~30 个 commit 是正常的，一个大 commit 是事故。

### 0.3 完成的定义（DoD）

一个任务只有同时满足下面 5 条才算"完成"，否则保持 pending 并在报告里写清楚卡在哪：

- [ ] 代码改完，`pnpm check` 通过（strict TS，无新增 `any`）
- [ ] `pnpm test` 全绿；新增逻辑有对应单测（纯函数优先，UI 逻辑抽成可测的纯函数再测）
- [ ] `pnpm build` 通过
- [ ] 触及 `src-tauri/` 时 `scripts\vsenv.cmd cargo check` 通过
- [ ] `docs/versions/` 对应记录已更新（改了什么 / 为什么 / 怎么自测）

### 0.4 报告格式（每完成 3~5 个任务输出一次 checkpoint）

```
## CHECKPOINT <时间> — 夜次 N
完成：P0-01 / P0-02 / P1-04
验证：pnpm check ✅ / pnpm test 52 passed ✅ / pnpm build ✅
偏离：P1-04 原计划用 X，实际改成 Y（原因：…）
风险：Z 需要人工验证（步骤已写入文档 §7.3 第 4 条）
下一步：P0-03
```

### 0.5 绝对不能做的事（违反 = 立即停止）

| 红线 | 原因 |
|---|---|
| 改 `identifier`（`com.mochi.pet`）或 `productName` | 会换掉用户数据目录，等于把用户聊天记录/待办/自定义素材全部"弄丢" |
| 执行 `git push` / `git tag` / 触发 CI 发布 | 部署纪律：必须由用户当次显式声明（AGENTS.md §2） |
| 提交任何 API Key、token、真实用户数据 | 安全红线 |
| 把 `bundle.targets` 改成非 `all` | v0.8.0 踩过：改窄会让 macOS CI 出不来 dmg |
| 为了过检查而删测试 / 加 `@ts-ignore` / 把类型改成 `any` | 检查形同虚设 |
| 大改架构（换状态管理库、引入 UI 框架、把 Agent 逻辑挪进 Rust） | 这是教学项目，架构本身就是交付物 |
| 声称"已验证"但实际没跑 | 宁可写 `[需人工]`，也不要编造结果 |
| 删除 `docs/learning/` 任何文件 | 学习文档是项目核心产出 |

### 0.6 本机环境的三个坑（省你半小时）

1. **本机 `cargo`/`tauri` 必须走包装脚本**：`scripts\vsenv.cmd <命令>`。
   直接 `cargo build` 会报 MSVC 链接错误（rustc 不自动探测环境，Git Bash 的 `link.exe` 还会遮蔽）。
2. **`pnpm` 走项目脚本**：`node node_modules/typescript/bin/tsc --noEmit` 这类直调
   等价于 `pnpm check`，在受限 shell 里比 `pnpm` shim 更稳。
3. **完整打包 `tauri build` 在当前沙箱里会失败**（`vcvars64.bat` 内部调 `reg.exe` 被安全策略拦，
   导致 `cl.exe` 环境不全）。**不要试图绕过**。打包验证交给用户，命令：
   `scripts\vsenv.cmd pnpm tauri build`。

## 1. 项目快照

### 1.1 技术栈

| 层 | 技术 | 说明 |
|---|---|---|
| 外壳 | Tauri 2（Rust 2.12 / CLI 2.12） | 三窗口：`pet`(220×260 透明无边框) / `chat`(480×640) / `alert`(320×200) |
| UI | React 18 + TypeScript strict + Vite | 全手写 CSS，无 UI 框架（刻意如此） |
| Agent | 全在 TS 层：provider 抽象 → SSE 流式 → tool loop → 记忆 → BM25 RAG | `src/agent/**` 不得 import React |
| 存储 | `tauri-plugin-sql`（SQLite `mochi.db`，5 表）+ `tauri-plugin-store`（settings.json） | 数据目录 `%APPDATA%\com.mochi.pet\` |

### 1.2 目录职责（AGENTS.md 的硬约束）

```
src/agent/      Agent 内核：core(循环/上下文) providers tools memory
src/services/   应用服务：db settings pet-state pet-assets timers presence reminders todos notifications
src/pages/      三个窗口的 React 入口（pet / chat / alert）
src/rag/        BM25 检索 + 快餐数据集
src/shared/     事件协议常量、跨窗口共享组件
src-tauri/      仅 Tauri 必需：窗口生命周期、托盘、2 个窄命令
```

**功能归属裁决**（新功能设计前必查 `docs/learning/07-agent-vs-app-boundary.md` §6.3）：
意图层归 Agent（"用户想干什么"），执行层归 Service（"怎么做"），存储层 100% 应用。
工具函数里不许写业务逻辑，只做薄封装。

### 1.3 已经固化的架构决策（不要推翻，要沿用）

1. **窗口控制权在 Rust**：前端只 `emit("ui://...")`，Rust 侧 `lib.rs` 统一执行。
   前端 capability 故意不给窗口控制权限（最小权限），别为了图方便去加 `core:window:allow-*`。
2. **宠物状态三层槽位**：`system ?? presence ?? mood ?? idle`（`services/pet-state.ts`）。
   系统状态期间情绪不抢占——这是"Agent 提议、应用裁决"的实现，别改成后写覆盖。
3. **时间基准是时间戳不是倒计时**：所有 timer 用 `deadline = Date.now() + …`，
   每秒 tick 只比较。别引入 `remaining--` 式计数（睡眠会漂移）。
4. **跨窗口通信用事件，不共享内存**：`src/shared/events.ts` 是唯一协议表，
   加事件必须两边（TS 常量 + `lib.rs` 的 `EVT_*`）同时改。
5. **宠物素材每次现扫**：`list_user_pet_assets` 每次切状态都 readdir，
   换来"放图即生效"。别改成 watcher（除非你能证明没有边缘 case）。

## 3. 体验体检：我们离"好用"还差什么

### 3.1 三个阶段的用户

| 阶段 | 用户状态 | 当前卡点 |
|---|---|---|
| **第一次打开**（0–5 分钟） | 装完看到一个不会动的团子 | ✅ 已解决（安装器中文 + 快速上手 + 首启引导）。剩余：引导之后没有任何"下一步"暗示，空聊天窗只有一行灰字 |
| **第一周**（日常） | 每天对话几次、开番茄钟、被提醒站起来 | 气泡缺失（回复只在聊天窗里）、右键菜单太薄、设置改了立刻生效但反馈弱、错误提示是技术黑话 |
| **长期**（一个月后） | 挂机常驻，主要用提醒/待办 | 位置不持久、没开机自启、没快捷键、没更新入口、宠物不能换大小 |

### 3.2 五条诊断结论

1. **表达通道太窄**：桌宠的灵魂是"在我旁边说一句话"。现在 Agent 的回复全部发生在
   480×640 的窗口里，用户必须主动打开窗口才能看到——这更像一个聊天工具，不像宠物。
   → P1-01 气泡是**投入产出比最高的一项**。
2. **设置是"工程师的设计"**：即时落盘（无保存按钮）本身是好设计，但字符级触发导致
   计时器被反复重置（P0-02）；错误提示暴露 `[bad-request]` 这类内部枚举（P1-07）。
3. **交互被发现性差**：单击重置计时、双击开聊天、右键出菜单，三个手势没有一个有提示
   （P1-02/P1-10）。新用户靠猜。
4. **系统集成只做了一半**：窗口位置不持久、没有自启、没有快捷键、多屏算错（P0-04/P1-05）。
   桌宠类应用这些都是"有就该有"的项。
5. **可观测性为零**：没有日志、没有版本信息、错误只 console。用户报"不好使"时无从下手
   （P0-06）。

### P0 —— 今晚必须清掉

#### P0-01 设置页外部链接点了没反应

- **现象**：设置里「还没有 Key？https://platform.deepseek.com」点了没有任何反应。
- **证据**：`src/pages/chat/SettingsTab.tsx` 用的是普通 `<a href>`；Tauri WebView 不会
  把外链交给系统浏览器，CSP 也不允许导航。
- **根因**：依赖里已有 `@tauri-apps/plugin-opener`（`Cargo.toml` 已 init），但前端从未调用。
- **修法**：
  ```ts
  import { openUrl } from "@tauri-apps/plugin-opener";
  // 用 <button> 替代 <a>，避免 WebView 尝试导航
  await openUrl("https://platform.deepseek.com");
  ```
  同时检查 `src-tauri/capabilities/default.json` 的 `opener:default` 是否覆盖 `open-url`；
  若被 scope 限制，显式加 `{ "identifier": "opener:allow-open-url", "allow": [{ "url": "https://*" }] }`。
- **验收**：点链接 → 系统默认浏览器打开；`pnpm check` 通过。
- **风险**：低。若权限配置写错，表现是 reject，用 `catch` 给出"请手动访问 <url>"兜底文案。

#### P0-02 设置项字符级落盘导致计时器被反复重置

- **现象**：把「站立提醒间隔」从 60 改成 30，输入过程中计时器被重排三四次；
  同理输入 API Key 每敲一个字符都写一次 `settings.json` 并广播全局事件。
- **证据**：`SettingsTab.update/updateKey/updateModel` 的 `onChange` 直接调用 `saveSettings`；
  `services/settings.ts#saveSettings` 每次 `emit(STATE_EVENTS.settingsChanged)`；
  `services/timers.ts#StandupService.reloadConfig` 收到事件就 `rearm("config")`。
- **根因**：把"字段级即时保存"做成了"按键级"，且事件不带变更内容，订阅方无法判断相关性。
- **修法（两层）**：
  1. `saveSettings` 加 300~400ms 防抖（模块内单例 timer，最后一次为准），
     或把数值输入改成 `onBlur`/`onKeyDown(Enter)` 提交；
  2. `settingsChanged` 载荷带上变更的 key 列表（`{ keys: string[] }`），
     `StandupService` 只在 `keys.includes("standupIntervalMin")` 时 rearm。
  > 注意：现在是 `saveSettings` 里 `Object.keys(settings)`（全量 key），不是"变更集"，
  > 订阅方看到的是"所有 key 都变了"，等于没信息。要么在 `update()` 处算 diff，
  > 要么显式传 `changedKeys` 参数。
- **验收**：连续输入 `30` 只产生 1 次写盘 + 1 次 rearm（给 settings 加一个可注入的
  `onPersist` 回调，单测里计数）；`pnpm test` 增加一条用例覆盖。
- **风险**：中。防抖会让"改完立刻关窗"丢最后一次写盘 → 必须在 `blur`/窗口隐藏时 flush。

#### P0-03 通知权限没有主动申请和状态展示

- **现象**：macOS 上第一次到点提醒可能什么也不弹；用户不知道通知有没有被系统禁掉。
- **证据**：`services/notifications.ts#notify` 只在"要发的时候"才 `requestPermission`，
  且失败只 `console.error`。
- **修法**：
  1. 宠物窗启动后（`pages/pet/main.tsx`）预热一次权限申请；
  2. 设置页「启用系统通知」旁显示真实权限状态（已授权 / 已拒绝 / 未询问），
     拒绝时给一行指引（Windows：设置 → 系统 → 通知；macOS：系统设置 → 通知 → Mochi）；
  3. `notify` 返回 `boolean`，让调用方能在失败时降级到宠物 `alert` 状态。
- **验收**：设置页能正确反映权限；`notify` 失败不再静默。
- **风险**：低。Windows 上 `isPermissionGranted` 恒为 true，注意别写成"必须询问"。

#### P0-04 宠物窗位置不持久 + 多显示器算错

- **现象 A**：把麻薯拖到屏幕中间，重启后回到右下角。
- **现象 B**：笔记本外接显示器时，麻薯出现在主屏而不是用户拖到的副屏；分辨率变化后可能跑到屏幕外。
- **证据**：`src-tauri/src/lib.rs#position_pet_bottom_right` 只在 `setup` 里跑一次，
  且固定用 `primary_monitor()`。
- **修法（按顺序）**：
  1. 位置持久化：引入 `tauri-plugin-window-state`（最省事），或在 Rust 侧监听
     `WindowEvent::Moved` 把坐标写进 `tauri-plugin-store`/一个 json，启动时恢复；
     恢复前校验坐标是否落在某个 `available_monitors()` 的可见区域内，否则回退右下角。
  2. 首次定位用**工作区**而非整屏尺寸：Windows 上任务栏在底部时，现在的算法会让
     麻薯压在任务栏上方（注释里已承认）。用 `monitor.work_area()` 之类的可用区域计算。
- **验收**：拖到副屏 → 退出 → 启动 → 回到副屏原位置；任务栏在底部时麻薯不被任务栏遮挡。
- **风险**：中高（涉及 Rust + 新插件）。**必须 `scripts\vsenv.cmd cargo check`**，
  且这是需要人工核验的项，做好 `[需人工]` 标注。

#### P0-05 macOS 未签名，用户双击被 Gatekeeper 拦下且没有说明

- **现象**：下载 `.dmg` 拖进 Applications，双击提示"无法打开，因为无法验证开发者"。
- **证据**：`docs/versions/v0.8.0` 明确写了"未签名"，但 README 的快速开始只写了 Windows。
- **修法**：
  1. README 加「macOS 首次打开」小节：右键 → 打开 → 仍要打开；或
     `xattr -dr com.apple.quarantine /Applications/Mochi.app`；
  2. 应用内「关于」里也提示一句（复用 P0-06 的关于区块）。
- **验收**：文档可执行，一个新用户照做能打开。
- **风险**：无（纯文档）。

#### P0-06 没有「关于 / 版本 / 数据目录」入口

- **现象**：用户反馈问题时无法自报版本；想备份数据也不知道文件在哪。
- **修法**：设置页底部加一块「关于」：
  - 版本号：`import { getVersion } from "@tauri-apps/api/app"` → `getVersion()`
  - 数据目录：`import { appDataDir } from "@tauri-apps/api/path"`（需要 `core:path:default`，
    检查 capability）
  - 两个按钮：「复制诊断信息」（版本 + 平台 + 数据目录，写入剪贴板）、
    「打开数据目录」（`revealItemInDir` 或 opener）。
- **验收**：能读到真实版本号；复制出来的文本能直接贴进 issue。
- **风险**：低（path/剪贴板权限要补）。

### P1 —— 体验硬伤，按顺序做

#### P1-01 宠物气泡（本轮最高价值项）

- **目标**：Agent 回复不再只出现在聊天窗——宠物头顶浮出一个小气泡，说 1~2 句，几秒后淡出。
- **实现建议（不要过度设计）**：
  1. `tauri.conf.json` 新增第四窗口 `bubble`：`transparent:true, decorations:false,
     alwaysOnTop:true, skipTaskbar:true, focus:false, visible:false`，尺寸约 260×140，
     新建 `src/pages/bubble/{BubbleApp.tsx, main.tsx, bubble.css}` + `bubble.html` 入口
     （照抄 `alert` 三件套即可）。
  2. Rust 侧加 `ui://show-bubble` 事件：定位到宠物正上方（复用 `show_alert` 的几何逻辑，
     抽成 `position_above_pet(window_label)`），`payload` 传文本 → 用事件把文本送给 bubble 窗。
     注意：现在 `show_alert` 是从 `listen_any` 回调里拿不到 payload 的写法，
     要改成 `listen_any<{text:string}>` 并把 payload 转发给窗口（`window.emit("bubble://text", …)`）。
  3. 由 `agentFacade.runTurn` 的 `done` 事件触发：终答落地后取前 60 个字符（按句号截断）
     发气泡；用户正在聊天窗里看着的时候**不发**（需要一个 `chatVisible` 状态，
     可由 chat 窗 `listen` 页面可见性后 emit 给宠物窗）。
  4. 自动消失：8 秒（`setTimeout` + CSS 淡出），点击气泡 = 打开聊天窗。
- **验收**：在宠物窗聊天（不打开聊天窗，走托盘/快捷键触发）→ 气泡出现并显示回复摘要；
  8 秒后消失；点气泡打开聊天窗。
- **风险**：中。新窗口会带来"多一个 WebView 实例"的内存开销（约 20~40MB），
  如果嫌重，**降级方案**：复用 `alert` 窗口，用不同 payload 切换内容样式。
- **教学价值**：这是"事件协议 + 多窗口"的最佳案例，实现后补到 `learning/06` 一小节。

#### P1-02 右键菜单太薄 + 表情演示不该出现在用户菜单里

- **现状**：`src/pages/pet/ContextMenu.tsx` 只有「打开聊天 / 隐藏麻薯 / 表情演示 / 退出」。
- **改成**：
  ```
  打开聊天
  待办（3）            ← 读 todoService.snapshot().length，0 条时显示「待办」
  番茄钟 · 专注中 12:34  ← 订阅 state://pomodoro-changed；空闲时显示「开始番茄钟」
  站立提醒 · 还剩 43 分钟
  ─────────────
  设置…               ← 打开聊天窗并切到「设置」Tab（需要 openChat 载荷支持 tab）
  暂停提醒 1 小时
  ─────────────
  隐藏麻薯
  退出 Mochi
  ```
  「表情演示」收进子菜单「调试 → 表情演示」，或只在 `import.meta.env.DEV` 下渲染。
- **注意**：菜单夹紧逻辑（`MENU_W/MENU_H` 常量）是硬编码的，项变多后必须改成
  先用 `ref` 测量真实尺寸再 clamp，否则一定溢出。这是当前代码里最容易踩的坑。
- **验收**：220×260 窗口里，菜单在四个角打开都不溢出；菜单项显示真实状态数字。

#### P1-03 托盘菜单与图标没有状态

- **现状**：`lib.rs#setup_tray` 三项静态菜单，tooltip 固定「Mochi 麻薯」。
- **改成**：
  - tooltip 动态：`Mochi · 专注中 12:34` / `Mochi · 该站起来了` / `Mochi`（由前端事件驱动，
    Rust 侧 `tray.set_tooltip()`）；
  - 菜单加「开始 / 停止番茄钟」「暂停提醒 1 小时」「设置…」；
  - 番茄钟运行时可考虑换托盘图标（两套 icon，`TrayIcon::set_icon()`）。
- **风险**：Rust 菜单项 id 与前端事件要一一对应，记得两边同步改名。

#### P1-04 聊天窗视觉割裂（直角 + 无阴影）

- **现象**：`decorations:false` 的窗口在 Windows 11 上是硬直角，贴桌面像一块补丁。
- **修法**：`tauri.conf.json` 的 `chat` 窗口加 `"transparent": true`，CSS 给 `.chat-shell`
  加 `border-radius: 12px; overflow: hidden; box-shadow: 0 12px 32px rgba(80,50,60,.18);`，
  `html,body` 背景改 `transparent`。
- **风险**：Windows 透明窗口 + WebView2 在某些显卡上有性能/闪烁问题；**如果出现拖影，
  立刻回退**（保留 `background` 方案，只做圆角不透明）。这是"宁可少做也不要退步"的项。

#### P1-05 流式输出结束才变 Markdown，视觉跳变

- **证据**：`src/pages/chat/ChatTab.tsx` 里 `e.streaming ? chat-msg__plain : <MarkdownView/>`。
- **修法**：流式也走 `MarkdownView`，用 `React.memo` + 80ms 节流（只在 `content` 变化时重渲染，
  `react-markdown` 对 2KB 内的文本足够快）。若实测卡顿，退回"纯文本 + 结束后替换"并加一个
  0.15s 的淡入过渡掩盖跳变。
- **验收**：流式过程中列表、加粗、代码块即时呈现，不闪。

#### P1-06 工具轨迹用技术黑话

- **证据**：`ChatTab.tsx` 的 `🔧 ${trace}`，实际渲染像 `🔧 todo_add ✓ · set_pet_state ✓`。
- **修法**：建一张映射表（`src/pages/chat/tool-labels.ts`）：

  | 工具 | 用户看到的文案 |
  |---|---|
  | `todo_add` / `add_todo` | 已加入待办 |
  | `todo_complete` | 已勾掉一条待办 |
  | `search_food` | 查了热量表 |
  | `create_reminder` | 设好了提醒 |
  | `start_pomodoro` | 开始专注 |
  | `remember` | 记住了这件事 |
  | `set_pet_state` | （不展示，内部动作） |

  失败时显示「X 没成功」而不是 `✗`；`set_pet_state` 完全不进列表（噪音）。
- **验收**：一轮带工具调用的对话，轨迹行是自然中文。

#### P1-07 错误提示是人话，不是枚举

- **证据**：`ChatTab.tsx` 的 `[{error.kind}] {error.message}`；`ProviderError.kind` 是
  `auth | network | rate-limit | bad-request | server | aborted` 之类的内部枚举。
- **修法**：建 `src/agent/error-text.ts`，把 `(kind, message)` 映射成
  「Key 好像不对，去设置里检查一下」+ 一个可点的动作按钮（去设置 / 重试 / 稍后再试）。
  同时保留原始 message 的折叠区（`<details>`），方便排查。
- **验收**：断网、错 Key、429 三种情况下，用户看到的是可执行的下一步。

#### P1-08 消息不能复制 / 不能重试

- **修法**：气泡 hover 出「复制」；最后一条 assistant 失败时出「重试」按钮
  （重发上一条 user 输入）。复制用 `navigator.clipboard.writeText`。
- **验收**：复制内容与渲染文本一致（不含 Markdown 标记的源码 vs 渲染文本——选渲染文本，
  用户预期是"我刚看到的字"）。

#### P1-09 引导的退出策略（补 §2.3 的已知缺口）

- 在 `WelcomeGuide` 底部加一行小字链接：「以后不再自动显示」→ 直接把 `onboardingDone`
  置 true 并关闭。默认行为不变（关窗后再启动仍会显示）。
- **为什么不全自动**：新用户第一次很可能只是切窗口，不该被判定为"看过了"。

#### P1-10 交互提示缺失（手势发现性）

- 首启引导讲了一次，但用户三天后就忘了。低成本补法：
  在宠物右键菜单里加一条静态提示行（不可点）：「拖动移动 · 单击重置站立 · 双击聊天」，
  灰色小字，永远在那。
- 进阶（P2）：首次拖动/首次单击后各弹一次气泡提示。

#### P1-11 站立提醒没有「稍后 5 分钟」

- **证据**：`src/pages/alert/AlertApp.tsx` 只有整卡点击 = ack。
- **修法**：卡片底部加两个按钮：「起来活动（重置）」= 现有 ack；「稍后 5 分钟」=
  新事件 `ui://standup-snooze`，StandupService 把 `deadline = now + 5min` 并清 alert 状态。
  注意 `tick()` 里 `state !== "armed"` 的判断要先 `state = "armed"`。
- **验收**：点稍后 → 弹窗关闭、宠物回 idle、5 分钟后再次弹出。

#### P1-12 空状态引导（聊天窗第一屏）

- **证据**：`ChatTab` 空态只有一行「跟麻薯说句话吧～试试：…」。
- **改成**：4 个可点击的"指令 chips"：`帮我加个待办`/`来个番茄钟`/`巨无霸多少热量`/
  `记住我晚上不喝咖啡`，点击直接填入输入框并聚焦（**不要自动发送**——自动发送会让
  用户觉得失去了控制权）。

#### P1-13 全局快捷键

- 引入 `tauri-plugin-global-shortcut`，默认 `Ctrl/Cmd + Shift + M` 打开聊天窗，
  设置页可修改（v1 先写死 + 一个开关也行）。
- **风险**：快捷键冲突（Windows 上被别的软件占用会注册失败）→ 失败要静默降级并
  在设置页提示"快捷键被占用"。

#### P1-14 开机自启

- `tauri-plugin-autostart`，设置页一个开关，默认关（不要默认开机自启，那是流氓行为）。

#### P1-15 宠物大小

- 设置项 `petScale: 0.8 | 1 | 1.2`，Rust 侧改窗口尺寸（`set_size`）并按比例调整位置
  （保持右下角锚点），CSS 用 `--pet-scale` 控制 `max-width/height`。
- **注意**：改尺寸后要重新 clamp 到屏幕内。

## 9. 风险登记（出现这些情况先停下想清楚）

| 风险 | 触发信号 | 应对 |
|---|---|---|
| 透明窗口导致渲染异常 | 聊天窗圆角后出现黑边/拖影/GPU 占用飙升 | 回退 `transparent:false`，只保留圆角背景 |
| 新插件权限漏配 | 运行时报 `not allowed` / `opener` reject | 去 `capabilities/default.json` 补最小权限，**不要**图省事加 `core:default` 之外的宽泛权限 |
| Rust 侧改动编不过 | `cargo check` 报 link/环境错误 | 确认走 `scripts\vsenv.cmd`；仍失败则回退这次 Rust 改动，把任务标 blocked |
| 气泡窗口内存/焦点问题 | 气泡抢焦点导致输入被打断 | 气泡窗口必须 `focus:false` 且不可获得焦点（`set_focusable(false)` 若可用） |
| 一晚上改了太多 | commit 数 > 40，或单 commit > 400 行 | 立即停，先收夜并写文档，未完成的列进 backlog |

## 附录 B — 文案规范（写 UI 之前看一眼）

1. **说人话**：不出现 `bad-request`、`tool_call`、`provider`、`SQLite` 这类内部词。
2. **给下一步**：错误提示必须含"你可以做什么"，不能只说"失败了"。
3. **短**：单行 ≤ 28 个汉字（聊天窗 480px 宽），标题 ≤ 12 字。
4. **不用感叹号堆情绪**：麻薯的性格是"软"，不是"亢奋"。
5. **中文标点**：句内用「」，并列用顿号，省略号用「…」。
6. **emoji 克制**：只在状态提示里用（🍅/⏰/🧍），一个气泡最多一个。

## 附录 C — 参考实现：设置防抖（P0-02 的最小改动版）

```ts
// src/services/settings.ts
let pending: AppSettings | null = null;
let timer: number | null = null;

/** 落盘防抖：最后一次输入后 350ms 才真正写 store 并广播 */
export function queueSave(settings: AppSettings, changedKeys: (keyof AppSettings)[]): void {
  pending = settings;
  if (timer != null) window.clearTimeout(timer);
  timer = window.setTimeout(() => {
    timer = null;
    const next = pending;
    pending = null;
    if (next) void saveSettings(next, changedKeys);
  }, 350);
}

/** 关窗/切 Tab 前调用，保证最后一次输入不丢 */
export function flushSave(): void {
  if (timer != null) { window.clearTimeout(timer); timer = null; }
  if (pending) { const next = pending; pending = null; void saveSettings(next, []); }
}
```

对应 `StandupService`：

```ts
await listen<{ keys?: string[] }>(STATE_EVENTS.settingsChanged, e => {
  const keys = e.payload?.keys ?? [];
  void this.reloadConfig().then(() => {
    // 只有"间隔"变了才重置计时；改通知开关不该把刚走的 40 分钟清零
    if (keys.includes("standupIntervalMin")) this.rearm("config");
  });
});
```

> 注意上面是"先重载配置再决定是否 rearm"，顺序反了会出现"用旧间隔重置"的竞态。
